# Stampede

**Flash-sale ticketing that never sells a seat twice.** 100 seats, thousands of buyers, one second.
Stampede is a working answer to the classic system design question *"design Ticketmaster"*: a
virtual waiting room, atomic seat holds, idempotent payments and a database that refuses to oversell
even when everything above it fails.

> Status: phase 1 (core engine + API) done. Next: workers + outbox relay, live WebSocket seat map,
> Next.js frontend, k6 load test, chaos mode, observability, hosting.

## Architecture

```
          ┌──────────── waiting room ────────────┐
buyer ──► │ JOIN: atomic ticket number (Lua)     │   admitted = burst + rate × seconds_open
          │ STATUS: rank vs admitted → pass      │   (pure function of time: no cron needed)
          └──────────────────┬───────────────────┘
                             │ signed admission pass (HMAC, stateless)
                             ▼
          ┌──────────── seat holds (Redis) ──────┐
          │ HOLD: Lua check-and-set + TTL        │   two clicks, same millisecond → one winner
          │ per-user hold limit, auto-expiry     │   time from Redis TIME, not app clocks
          └──────────────────┬───────────────────┘
                             ▼
          ┌──────────── checkout ────────────────┐
          │ 1 replay   Idempotency-Key seen?      │
          │ 2 lock     identical request in flight│
          │ 3 claim    still your hold? extend it │
          │ 4 pay      fake gateway, idempotent   │
          │ 5 commit   order+ticket+outbox, 1 txn │ ◄── Postgres UNIQUE(event, seat): last line of defence
          │ 6 sold     update Redis (repairable)  │
          └───────────────────────────────────────┘
```

**Redis is the fast path, Postgres is the source of truth.** If Redis loses its state, a second
buyer can get a hold on a sold seat, but the database rejects the second ticket and the buyer is
refunded automatically (`tests/test_checkout.py::test_database_is_the_last_line_of_defence`).
`POST /events/{id}/resync` rebuilds Redis from Postgres.

## Design decisions (and why)

| Problem | Decision | Trade-off |
|---|---|---|
| Two buyers, one seat, same millisecond | Redis Lua script (atomic check-and-set) | Redis becomes critical; Postgres constraint covers its failure |
| Seat held but never paid | `SET PX` TTL, auto-release | Hold length is a product choice (120s default) |
| Hold expiring mid-payment | `claim` extends the hold before charging | A slow payment can hold a seat up to the grace period |
| Thousands arrive at once | Waiting room, admission as a function of time | Fixed drain rate; does not adapt to live load yet |
| Seat picking must stay fast | Stateless HMAC admission passes | Passes cannot be revoked before they expire |
| Double click / network retry on Pay | Idempotency-Key: replay, in-flight lock, idempotent gateway | Keys must be generated by the client |
| "Ticket issued" must follow the sale | Transactional outbox in the same transaction | Messages are delayed until a relay publishes them |
| Bots / floods | Token bucket per client in Redis | Per-IP limits are coarse behind shared NATs |
| Cold connections under a spike | Bounded blocking pool + warm-up at startup | Measured: TLS connect to hosted Redis ~0.4s vs ~30ms per command |
| Sharding later | All event keys share a `{hash tag}` | One hot event still lives on one shard |

## Run it

```powershell
docker compose up -d                          # local Redis + Postgres (free, unlimited)
py -m venv .venv
.\.venv\Scripts\pip install -r requirements-dev.txt
.\.venv\Scripts\python -m pytest              # 24 tests, real Redis + Postgres, no keys
```

## Tests that matter

- 200 buyers race for one seat: exactly one wins
- 100 buyers, 10 seats, everyone tries every seat at once: every seat sold exactly once
- double click on Pay: one charge, one order
- Redis wiped after a sale: database blocks the oversell, buyer refunded, retry gets the same answer
- 300 concurrent joins get 300 unique places in line

## Free hosting
